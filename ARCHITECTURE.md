# Architecture

One PostgreSQL database, one synchronous FastAPI service, and four standalone Angular views. Nginx serves the compiled UI and proxies `/api` to FastAPI on the same origin. Compose waits for PostgreSQL, applies Alembic migrations, starts the API, then exposes the UI on port 8080. Seeding is explicit and repeatable.

`backend/migrations` owns the schema. Medicines have non-overlapping, half-open rule periods enforced by a PostgreSQL exclusion constraint. Dispenses reference the rule used for their original evaluation. Attempts retain canonical request payloads and immutable success/rejection outcomes; normalized reasons make rejected attempts inspectable without parsing response JSON. A data migration moves existing JSON reason arrays into rows and reconstructs them on downgrade.

`app/main.py` defines the HTTP boundary and common exception contract. `schemas.py` validates typed input. `catalogue.py` holds indexed read queries and filter-bound cursors. SQLAlchemy Core owns pooled connections and transaction lifetimes; explicit bound SQL makes the relevant locks and query plans easy to inspect without a second ORM schema.

`rules.py` selects the rule at occurrence time and splits periods when a new version supersedes one. `dispenses.py` owns the dispense transaction and rule evaluation. It locks the idempotency key, checks for a saved outcome, takes a shared medicine row lock, then locks the patient/medicine pair. Only then does it calculate rolling totals, validate affected later windows, and write a dispense plus its outcome or only a rejection outcome. A normal rejection commits rather than raising through a rollback. Rule edits acquire an exclusive medicine row lock. UTC storage and explicit Johannesburg business boundaries meet at these services.

The Angular views are medicine search, medicine detail/history, dispense capture and patient ledger. Each view owns its state through signals; nothing is shared between views. Route parameters are the source of truth for the selected medicine and ledger patient, so reloads and history navigation reload the reused view instead of showing stale data. A small `Pager` cancels superseded searches, implements cursor navigation, retries a failed page and aborts its in-flight request through `DestroyRef` when its view is destroyed; route subscriptions end with `takeUntilDestroyed`. Capture keeps unresolved payloads and keys in tab-local session storage; fields remain locked until an exact retry confirms the outcome. Definite rejections render all reasons beside their fields. A changed rejected payload receives a new key.

Tests exercise real PostgreSQL constraints, migrations, temporal boundaries, idempotency, HTTP errors and pagination. Concurrency tests observe actual blocked PostgreSQL connections before releasing competing HTTP requests. Playwright covers the four-view workflow and failure-prone form/search state. The benchmark measures the full Nginx→FastAPI→PostgreSQL HTTP path and records actual query plans. No authentication, cloud deployment, clinical patient model, state framework, or CSS framework is included.
